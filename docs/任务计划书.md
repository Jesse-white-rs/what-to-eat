# 任务计划书：今天吃什么 — Supabase 真后端重构

> 项目：`今天吃什么`（随机选餐静态站）
> 目标：将现有「伪前后端（data.txt + localStorage）」架构重构为「Supabase 真前后端」架构
> 日期：2026-08-19

---

## 一、项目现状

| 层 | 现状 | 问题 |
|---|---|---|
| 数据存储 | `data.txt`（仓库内 JSON 文件）+ `localStorage` | 改数据需手动导出/上传替换文件，无法多端实时同步 |
| 前端 | 静态 HTML/CSS/JS，fetch 读取 data.txt | 只能"读"，写操作是本地假象 |
| 部署 | GitHub Pages + Actions | 无服务端，无法直接写库 |

## 二、重构目标

1. **真实数据库**：使用 Supabase（PostgreSQL）作为唯一数据源，多端实时同步；
2. **真实增删改查**：页面所有操作直连数据库 API；
3. **静态托管兼容**：GitHub Pages 只能放静态文件，因此采用 **PostgREST + RLS 匿名策略** 模式——前端直接调用 Supabase REST API，无需自建后端；
4. **离线降级**：Supabase 不可用时（项目暂停/断网）自动降级到 localStorage，不白屏；
5. **旧数据迁移**：把 `data.txt` 中的菜谱/历史一键导入 Supabase。

## 三、总体架构

```
┌─────────────────┐     HTTPS + PostgREST REST API      ┌─────────────────┐
│   GitHub Pages  │ ───────────────────────────────────▶ │    Supabase     │
│  (index.html /  │     apikey: publishable_key          │  PostgreSQL 16  │
│   script.js)    │                                      │  - dishes       │
│    纯静态前端    │ ◀─────────────────────────────────── │  - pick_history │
└─────────────────┘      JSON 响应                        └─────────────────┘
        │                                                        ▲
        │ localStorage（离线降级缓存 + 离线变更队列）              │  RLS 匿名读写策略
        ▼                                                        │
  ┌─────────────────────┐     只读     ┌────────────────────────┘
  │ 用户浏览器           │             │
  │ · 在线：实时读写云端 │             │
  │ · 离线：本地缓存+队列│             │
  └─────────────────────┘
```

### 密钥使用策略（重要）

| 密钥 | 用途 | 存放位置 |
|---|---|---|
| `SUPABASE_PUBLISHABLE_KEY`（`sb_publishable_...`） | 前端页面调用 PostgREST API | 写入 `script.js`（GitHub Pages 公开部署，本身就是公开密钥） |
| `SUPABASE_SECRET_KEY`（`sb_secret_...`） | 迁移/种子脚本（等同 service_role，全权限） | 仅存于本地 `.env`（已加入 `.gitignore`），**禁止提交到公开仓库** |
| `SUPABASE_URL` | 前端 API 地址 | 写入 `script.js` |
| `SUPABASE_JWKS_URL` | Auth 校验（当前匿名模式不需要，保留备用） | 文档记录 |

## 四、数据库设计

### 4.1 `dishes`（菜谱表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | uuid | PK, default `gen_random_uuid()` | 主键 |
| `name` | text | NOT NULL | 菜名/餐品 |
| `store` | text | default '' | 店名 |
| `category` | text | default '' | 分类 |
| `price` | numeric | 可空 | 价格（元） |
| `note` | text | default '' | 备注 |
| `pick_count` | int | default 0 | 被选次数 |
| `last_picked` | timestamptz | 可空 | 最近被选时间 |
| `created_at` | timestamptz | default `now()` | 创建时间 |

### 4.2 `pick_history`（选择历史表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | uuid | PK | 主键 |
| `dish_id` | uuid | 可空（dish 删除后保留快照） | 关联菜谱 |
| `dish_name` | text | NOT NULL | 菜名快照 |
| `dish_store` | text | default '' | 店名快照 |
| `dish_category` | text | default '' | 分类快照 |
| `created_at` | timestamptz | default `now()` | 选择时间 |

### 4.3 索引
- `pick_history(created_at desc)` — 历史列表按时间倒序查询
- `dishes(category)` — 分类筛选

### 4.4 RLS 策略（匿名公共读写）
```sql
ALTER TABLE dishes ENABLE ROW LEVEL SECURITY;
CREATE POLICY "dishes_public_all" ON dishes FOR ALL USING (true) WITH CHECK (true);
-- pick_history 同理
```
> 说明：这是公开"今天吃什么"共享站点的取舍——任何访问者均可增删改菜谱，以匿名权限换取无需登录的零门槛使用。数据敏感度低，风险可接受。

## 五、前端改造方案

### 5.1 数据层（`script.js` 重构）
- 自实现轻量 **PostgREST 客户端**（纯 `fetch`，零依赖，避免 CDN 加载失败风险）：
  - `GET /rest/v1/dishes?select=*&order=created_at.asc`
  - `POST /rest/v1/dishes`（新增）
  - `PATCH /rest/v1/dishes?id=eq.{id}`（编辑/累加 pick_count）
  - `DELETE /rest/v1/dishes?id=eq.{id}`
  - `POST /rest/v1/pick_history`（写入历史）
  - `DELETE /rest/v1/pick_history?id=neq.00000000-0000-0000-0000-000000000000`（清空历史）
- 请求头携带 `apikey: <publishable>` + `Authorization: Bearer <publishable>`
- 错误处理：401/网络错误 → 进入离线模式

### 5.2 状态与降级
| 模式 | 触发条件 | 行为 |
|---|---|---|
| `cloud` | Supabase 连通 | 读写直接落库，localStorage 作镜像缓存 |
| `local` | Supabase 401/断网 | 读写本地缓存，变更进入**离线变更队列**（`localStorage`），顶部黄色横幅提示 |
| 恢复 | 再次连通（刷新/手动重试） | 自动把队列中的变更推送云端 |

### 5.3 UI 调整
- 顶栏状态灯增加「云同步中 / 云同步 OK / 离线本地模式」三态；
- 数据同步面板改为：**云端状态、离线队列条目数、导出备份、一键重连**；
- 保留 data.txt 导出（降级为"备份"功能，不再作为主数据源）。

### 5.4 随机选餐逻辑
- 逻辑不变（加权随机，pick_count 越小权重越高），但 `pick_count + 1` 与 `last_picked` 更新、历史写入均为真实云端操作。

## 六、迁移与初始化

### 6.1 数据库初始化（用户需在 Supabase 控制台执行）
1. **恢复项目**：登录 https://supabase.com/dashboard → 找到项目 `eajpuqbmtlcuxtkhawfn` → 若处于 Paused 状态，点击 **Restore project**；
2. 打开 **SQL Editor** → 执行 `supabase/migration.sql`（建表 + 索引 + RLS + 可选种子数据）；
3. 确认 Keys：Settings → API，核对 publishable / secret key 与提供的值一致（如不一致需更新前端常量）。

### 6.2 旧数据迁移脚本
- `scripts/setup.mjs`（Node ≥18，本地开发工具）：
  - 读本地 `.env` 中的 `SUPABASE_SECRET_KEY`；
  - 检测 `dishes` 表是否存在（`HEAD /rest/v1/dishes`）；
  - 存在则把 `data.txt` 中的 `dishes[]` / `history[]` 批量 INSERT 进去（幂等：按 name+store 去重）；
  - 输出逐项结果。

## 七、部署方案

- 沿用现有 GitHub Actions（`deploy.yml`），推送 `main` 自动发布；
- `scripts/`、`supabase/`、`.env` 不参与构建，不影响页面；
- 前端仅依赖 Supabase 域名，无需同源。

## 八、风险与注意事项

| 风险 | 应对 |
|---|---|
| ⚠️ **项目当前返回 401，疑似已暂停/密钥失效（已实测）** | 需先在控制台恢复项目；前端已做离线降级，不会白屏 |
| Secret key 泄露 | 仅存本地 `.env`，`.gitignore` 排除；严禁写入前端 |
| 匿名 RLS 全开 | 本站为公开共享站点，风险可接受；如需私密可后续改为 Supabase Auth 登录 |
| PostgREST 返回 401 时前端误判 | 统一包装为"云不可用"状态，不抛未捕获异常 |
